1. Project Overview
The project is a unified digital platform for Tvarita Arts Collective that connects the public, traditional artists, schools/corporates, and the Tvarita administration. The platform is intended to support discovery of Indian folk and tribal art forms, artist visibility, learning and community engagement, bookings, product sales, knowledge preservation, and organizational analytics.
The supplied problem statement describes Tvarita's current operations as fragmented across spreadsheets, WhatsApp, Instagram, email, and manual documentation. The proposed platform therefore acts as a single digital ecosystem rather than only an e-commerce site. It also needs to be lightweight, visual, multilingual, mobile-friendly, and usable on low-end Android devices with intermittent connectivity.
Source basis: Tvarita problem statement and the four dashboard plans supplied in this conversation. The exact 4-portal structure below is the team's implementation design, not a literal requirement that the source document calls 'four portals.'

20. Security & Validation Requirements
Hash passwords with bcrypt/bcryptjs; never store plaintext passwords.
Sign JWTs with a strong secret and short access-token expiry. If refresh tokens are used, store them securely and rotate/revoke them.
Enforce role authorization in Express middleware for every protected route.
Validate request bodies with a schema library such as Joi/Zod/express-validator.
Use helmet, CORS configuration, rate limiting and request-size limits.
Sanitize user-generated text and protect against injection/XSS where applicable.
Validate upload MIME type, extension, size and ownership before sending to Cloudinary.
Razorpay payment verification must happen on the server; never trust a client-provided 'payment successful' flag.
Verify Razorpay webhook signatures before changing payment/order status.
Use MongoDB indexes for email, slug, art-form references, event dates and common search fields.
Log security-sensitive events without logging passwords, JWTs or payment secrets.
Use HTTPS in deployment and keep all secrets in environment variables.

22. PWA & Low-Connectivity Strategy
Use a responsive mobile-first UI, especially for the Artist Portal.
Add Web App Manifest for installability.
Use a service worker to cache the application shell and selected public discovery data.
Cache low-risk read-only content such as art-form descriptions and public artist profiles; avoid caching sensitive account/payment data in insecure storage.
Show clear offline/poor-connectivity states and retry failed requests.
Optimize images through Cloudinary transformations and lazy loading.
Keep pages lightweight and avoid unnecessary large bundles.
23. Razorpay Sandbox Integration Flow
Client selects a paid event/experience or product checkout.
React sends checkout details to POST /api/payments/orders or the relevant booking/order endpoint.
Express validates the amount from MongoDB rather than trusting a client-supplied amount.
Backend creates a Razorpay Sandbox order using the server-side Razorpay credentials.
Backend returns the Razorpay order ID to React.
React opens Razorpay Checkout using the returned order ID.
After checkout, React sends the payment identifiers/signature to POST /api/payments/verify.
Backend verifies the Razorpay signature and updates Payment + Booking/Order atomically as far as practical.
Razorpay webhook events are received at POST /api/payments/webhook and verified before updating final state.
Frontend receives the updated booking/order status and shows confirmation.
24. Cloudinary + Multer Upload Flow
React sends multipart/form-data to the appropriate upload endpoint.
Multer validates and temporarily handles the uploaded file.
Backend checks authenticated user/artist ownership and file constraints.
Backend uploads the file to Cloudinary.
Cloudinary returns secure URL/public ID and optional metadata.
MongoDB stores only the media URL/public ID and associated resource metadata.
On deletion, backend verifies ownership/admin permission and removes the Cloudinary asset if required.
25. Socket.IO Realtime Scope

30. Final Project Definition
Tvarita Digital Folk & Tribal Arts Ecosystem is a role-based MERN platform with four user experiences: Public/Civilian, School/Corporate, Artist, and Tvarita Admin. The public side focuses on discovery and sustained engagement; the institutional side focuses on organized cultural experiences and requests; the artist side focuses on digital visibility, requests, events, earnings and products; and the admin side provides centralized operations and impact analytics.
The backend should be treated as the central source of truth for authentication, authorization, artist and art-form data, event/request/booking state, marketplace orders, payment verification, media metadata, notifications and analytics. The React frontend should consume these capabilities through versionable REST APIs under /api, with Socket.IO used only for realtime interactions.
